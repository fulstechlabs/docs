title: "Security and Data"
description: "How Time in Status stores workflow history, protects report access and retains export files."
---

Time in Status runs on Atlassian Forge and uses Jira Cloud APIs. Workflow data
and saved configuration stay within Jira and Atlassian-hosted app storage.
The app has no external backend or external runtime analytics service.

## Where your data is stored

| Location | Purpose |
| --- | --- |
| App-managed Jira custom field | A replaceable workflow snapshot for each issue: Jira source revision, status IDs and visit timestamps, assignee account IDs and ownership timestamps. It does not store report totals, copied assignee profile names or email addresses. |
| Forge SQL | Working calendars, saved report configurations, report schedules and background export job information. Saved JQL contains the query entered by the report owner. |
| Forge Object Store | Temporary CSV and XLSX files generated by background exports. Files expire after 24 hours. |
| Your browser | Last-used report inputs. These do not synchronize across devices and may be lost when browser storage is cleared. |
| Request memory | Jira responses, current display names and calculated results used while processing a request. |
| Your downloaded files | CSV and XLSX copies that you save. You control their storage, sharing and deletion. |

## How workflow caching works

Jira history is the source of truth for calculations. The workflow snapshot
helps the app reuse history it has already read, making subsequent reports faster.
Before reusing it, the app checks the issue identity, Jira revision and calculation
version. When a snapshot is missing or no longer suitable, the app reads Jira
history again and replaces the snapshot where the workflow field is available.

Snapshots contain source visits rather than one user's calculated report totals.
Changing a calendar or timezone recalculates the same UTC visits with the selected
settings. You do not need a separate workflow snapshot for each user or calendar.

The app retrieves display names from Jira when needed. If a name is unavailable,
it displays the unchanged account ID. A failed name lookup does not change
historical ownership or durations. Assignee time measures elapsed ownership,
not logged work.

## Report access and sharing

Interactive reports retrieve Jira data using the signed-in user's permissions.
Sharing a saved report shares its configuration; each viewer's results are
calculated using their own Jira access. Dashboard reports follow the same rule.
The app does not provide a separate role-management system.

Saved reports are private unless their owner shares them. Review saved JQL and
report settings before sharing because other viewers can see that configuration.
Jira administration permission is required for calendar administration and
workflow-field setup.

Scheduled reports run using the owner's current Jira permissions. Sharing a
configuration does not grant another user access to the owner's export files.
After downloading a file, you are responsible for who receives that copy.

## Background exports and retention

Large CSV and XLSX exports continue after you close the browser tab. Return to
**Large and XLSX exports** to check progress and download the completed file.
Download files within 24 hours; once a file expires, create a new export.
A file already saved on your computer is unaffected by this expiry.

The app checks for due schedules and interrupted export jobs every hour.
Scheduled runs therefore do not promise execution at an exact minute.
Scheduled processing requires an active app license.

Daily maintenance removes failed, cancelled and expired export job records once
those records are more than seven days old. Removal occurs on the next eligible
maintenance run. Temporary files expire independently of these job records.
Saved reports and calendars are reusable configuration, not temporary exports.

## Installation and account changes

Installation and upgrades prepare app storage. Setup can resume after an
interruption; the app shows progress until reports are available. Issues created
before installation can be calculated from the history Jira provides without
waiting for a bulk historical import.

When Jira sends an account-deletion event, the app removes that account's owned
saved reports, schedules and export job records. It does not rewrite Jira issue
history or change historical ownership intervals. Temporary export files remain
subject to their expiry. Last-used preferences are stored in the browser.
